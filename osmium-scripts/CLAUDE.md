# OSM pipeline and map data deploy

`prepare.sh` (the pipeline behind `npm run prepareMapData`), `extracts.txt` (add a line to add a country), and `deploy.sh` / `remote-deploy.sh` (`npm run deployMapData`).

## prepare.sh

- Output: `data/pruned.geojson` for every region (a region is a bbox applied on read), plus `pruned.sources` (each extract's cut date) and `pruned.inputs` (each extract's `.source`, i.e. exactly which file or diff and the filter, plus the git hashes of `prepare.sh` and `src/scripts`). Naming extracts, or a path prefix ending at `/` (`-- asia/japan`), builds `data/pruned-partial.geojson` instead. Importing that still replaces the whole map.
- Always each extract's latest (`-latest` resolved to the dated file it redirects to). The next download runs in the background while one is filtered or a cached one updated, disk permitting (beside the updates it leaves room for the largest rewrite still to come). `OSMIUM_POOL_THREADS` is raised to at least 2: libosmium's own default (CPUs − 2, at least 1) leaves the server's 2 vCPUs a single compression worker.
- Merged with `osmium merge -H` + `time-filter`. Neighbouring extracts overlap and carry the same way in two versions, which a plain merge writes as two `railway_parts` rows with one id.
- Europe's list mirrors Geofabrik's Europe page, one extract per country (the continent won't fit the server's disk). The exceptions are the combination regions, Iceland and the Azores, and Russia goes in as federal districts. That way there is track everywhere on the admin map. A route crossing a region missing from the list goes invalid on import. Japan is one extract.
- Filtered extracts are **kept** under `data/extracts/<geofabrik path>` beside a `.source` (dated file + `RAIL_FILTER`). They are re-downloaded only when `-latest` points elsewhere or the filter changed. An extract removed from `extracts.txt` is deleted (unless `EXTRACTS_FILE` names a trial list); `--fresh` deletes them all.
- **Raw cache** (`RAW_CACHE`, from the environment or `.env`; the server sets it): directories that keep the raw extracts, filled in the order listed (`"data/raw /mnt/<volume>/osm-raw"`), each optionally capped in GB (`data/raw:11`). On the data disk the cache never goes below `DATA_DISK_RESERVE_GB` free (`prepare.sh`, which `remote-deploy.sh` asks for its pre-check), so no cap is needed there. But cached extracts grow with every update, in place, so the data disk drifts a few MB under the reserve. That is why `remote-deploy.sh` runs `prepare.sh --make-room` before its pre-check (measured in MB): it moves cached extracts off the data disk to another cache directory (the smallest file that covers the shortfall first, copied as `.part`, then renamed), or deletes them where no directory has room. A cached extract found in two directories keeps the first copy. A cached extract is brought up to date in place with Geofabrik's daily diffs (`pyosmium-up-to-date`, apt `pyosmium`) instead of downloaded, and its `.source` records the replication sequence number instead of a dated file. Diffs need the whole extract, never a filtered one. A file whose header is not on `<extract>-updates`, or one over 60 days old, is dropped and downloaded whole. A failed update, or no room for the rewrite, stops the run and keeps the file. A directory that doesn't exist is skipped. **On a volume, name a directory inside the mount point, never the mount point itself**: unmounted, the mount point is an empty directory on the root disk and would be filled. `--fresh` keeps the cache. Unset, nothing changes.

## Deploy (`deploy.sh` → `remote-deploy.sh`)

- Run locally. The work happens **on the server**, one plink call per step.
- Pulls the server's checkout of `main`. It refuses while local commits are unpushed or `osmium-scripts/`, `src/scripts/` or `package*.json` have uncommitted changes (`src/lib` only warns). Runs `npm ci` when `node_modules` wasn't installed from the current lockfile.
- Prepares the map there (no date: always the latest extracts) and imports it. The log (`data/deploy.log`) streams over `plink -t`, and **the deploy stops when that session ends**. Windows plink never forwards Ctrl+C, so the hangup is the only signal. Rerunning resumes: a pruned file prepared from the current extract list since the last successful deploy is reused. `--follow` shows a running deploy (Ctrl+C there stops it too) or the last log. `--fresh` discards prepared files.
- **It asks before it starts.** After the pull, `remote-deploy.sh --check` lists each extract's date in the deployed map against the latest (`europe/austria  2026-11-02 -> 2026-11-03`, `-> unchanged`) and whether the code changed, and ends with a verdict line (`new` | `unchanged`) that `deploy.sh` acts on: `unchanged` stops there, `new` asks `Deploy? [y/N]` (`--yes` skips it; a closed stdin is a no). `prepare.sh --latest-dates` (downloads nothing) prints each extract's date **and the `.inputs` record a run would write**: `replication <seq>` from `state.txt` for a cached extract, the dated file name otherwise. **"Unchanged" is decided on those records, the run's own test made ahead of it, never on dates**, because an `unchanged` verdict means the run never starts. So anything unpredictable is new: an `unknown` record on either side (Germany redirects to a mirror's undated `-latest`, so uncached it is always rebuilt), a download that would be cached. The code line comes from `prepare.sh --code-inputs`, one definition with the run's. Forced, reusing a prepared map, or no `.inputs` record all count as `new`, and a forced run goes ahead even when Geofabrik doesn't answer the check.
- **Nothing new, nothing done.** The server keeps the deployed map's `.inputs` (`data/deployed-extracts.inputs`) beside its dates (`data/deployed-extracts.txt`, the only record; nothing is committed). `prepare.sh` gets it as `DEPLOYED_INPUTS` and stops after step 1 when everything matches, with no output (and deletes a failed run's intermediates). `remote-deploy.sh` then records the status `unchanged`, which `deploy.sh` reports as nothing to deploy. Data, filter, pruning and import changes all count as new. `src/lib` doesn't (route recalculation: `verifyRouteData`), hence `--force` (`--fresh` implies it). A forced run leaves `data/deploy.force` until it succeeds, so its rerun is forced too. `importMapData` deletes the `.inputs` record as it starts, because any import (a manual one too) replaces the map it describes. Anything unknown (no `.source`, no git) never matches.
- `remote-deploy.sh --state` is how pulls detect a running deploy.
- **Output.** `prepare.sh` prints plain ASCII. Each extract's lines start with its name padded to one column (`say`), and the counter appears only on an extract's last line (`finish`, "done 3/42", in the order they finish), because downloads and filters overlap. `deploy.sh` switches a Windows console to UTF-8 (`chcp.com 65001`) for the run and restores it, since the server's log carries station names; in code page 437, "✓" shows as "Γ£ô". Only the import's recalculation summary is parsed (`deploy.sh`), so the rest of the wording is free to change.
- The server needs `osmium-tool` and `pyosmium` (apt) and swap (osmium needs ~2GB to filter a country).
- A successful deploy deletes `data/pruned.geojson`, which is kept only to resume a deploy that failed at the import.
